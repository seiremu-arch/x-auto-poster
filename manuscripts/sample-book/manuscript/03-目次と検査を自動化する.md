# 第3章　目次と検査を自動化する

## 目次は2種類ある

「目次」と一言でいっても、KDPに入稿するときには性質の違う2つを用意することになる。

1. **リンク付き目次** — 本文の先頭に置く、タップで各章に飛べるページ
2. **目次フィールド** — Wordが自動生成する、ページ番号付きの目次

電子書籍にページ番号は存在しないので、必要なのは1だけだ。逆にペーパーバックでは2が要る。本書のパイプラインでは、これを設定で切り替える。

```yaml
ebook:
  toc:
    style: link   # リンク付き目次
print:
  toc:
    style: field  # 目次フィールド(ページ番号付き)
```

`both`を指定すれば両方出る。

## リンク付き目次の仕組み

リンク付き目次は、見出しにブックマークを打ち、目次側からそこへリンクするだけで作れる。

```xml
<!-- 見出し側 -->
<w:bookmarkStart w:id="1" w:name="_Toc00001"/>
<w:r><w:t>第3章　目次と検査を自動化する</w:t></w:r>
<w:bookmarkEnd w:id="1"/>

<!-- 目次側 -->
<w:hyperlink w:anchor="_Toc00001">
  <w:r><w:t>第3章　目次と検査を自動化する</w:t></w:r>
</w:hyperlink>
```

ブックマーク名を`_Toc`で始めておくと、Wordの目次フィールドからも同じアンカーが使われる。目次の項目をどの階層まで載せるかは、設定の`depth`で決める。`2`なら`##`まで、`1`なら章だけだ。

## 入稿前チェックという工程

自動化して最も効くのが、実は組版よりも検査のほうだ。KDPの審査で差し戻される理由の多くは、事前に機械が見つけられる。

- 内容紹介が4000文字を超えている
- キーワードが8個以上ある
- 表紙の縦横比が推奨から外れている
- 本文画像の解像度がペーパーバックに足りない
- 原稿に書きかけのメモ(未処理マーカー)が残ったままになっている

これらをビルド前に走らせて、エラーがあればビルドを止める。

```bash
python scripts/build_book.py manuscripts/sample-book --check-only --strict
```

`--strict`を付けると警告もエラー扱いになる。GitHub Actionsのワークフローに入れておけば、原稿をpushするたびに検査が回る。

## 工程が回りはじめると

ここまで組むと、原稿を直してからKDPに入稿できるファイルが揃うまでが数秒になる。推敲のたびに組版をやり直す苦痛がなくなり、直しの回数だけが増えていく。

工程を自動化する目的は、時間の節約そのものではない。**書き直すコストを下げて、書き直せるようにすること**だ。
