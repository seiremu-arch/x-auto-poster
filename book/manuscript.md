# はじめてのAI開発
## ― Cursor・Claude Code・GitHubと歩く、物語のはじまり ―

(仮題・第一稿)

# 序章 光、決意する

---

> ものがたり

閉店作業を終えたカフェ「ひかりや」の店内に、光(ひかり)はひとり座り込んでいた。テーブルの上には、表紙が反り返った予約ノート。今日だけで三件、ダブルブッキングをしてしまった。

一件目は電話。二件目はLINEのメッセージが埋もれて見落とした。三件目は、常連の田村さんに直接「今日は満席で……」と頭を下げるしかなかった。田村さんは笑って許してくれたけれど、光の胸には重いものが残った。

「紙とLINEでやってるの、もう限界かもな」

独り言がこぼれた。予約管理アプリを入れようかとスマホで検索してみる。しかし、どれも月額料金が高いか、ひかりやの座席数や一人客・グループ客の区別といった細かい運用に合わなかった。

「だったら、自分で作れないかな」

そのとき頭をよぎったのは、常連客であり元エンジニアだという「先生」こと佐伯さんの顔だった。カウンター越しに、彼が時々スマホの画面を見ながら「最近はAIに話しかけるだけでアプリが作れるらしいですよ」と笑っていたのを思い出す。

半信半疑だった。プログラミングなんて学生時代に授業で少し触れただけ。けれど、ノートに書きなぐったダブルブッキングの記録を見つめているうちに、光は決めた。

「作ってみよう。自分のお店のためのアプリを」

それが、光の長い――けれど思っていたよりずっと近くにあった――開発の旅の始まりだった。

---

## 本書について

本書は、プログラミングの経験がまったくない人が、AIを相棒にしてアプリケーションを作れるようになるまでの過程を、物語と解説の両方から描く一冊です。

主役は三つの道具です。

- **Cursor** ―― AIの力を組み込んだコードエディタ。文章を書くようにコードを書き、AIに相談しながら作業を進められます。
- **Claude Code** ―― ターミナル(文字だけの操作画面)の中で対話しながらコードを書き、動かし、直してくれるAIエージェントです。
- **GitHub** ―― 書いたコードの変更履歴を記録し、世界中の開発者と共有・共同作業するための土台となるサービスです。

この三つは、それぞれ役割が違います。Cursorは「作業机」、Claude Codeは「手を動かしてくれる相棒」、GitHubは「作業の記録を残す金庫であり、誰かと一緒に作業するための広場」だとイメージしてください。本書を読み終える頃には、この三つがどう連携し合っているかが、感覚としてつかめているはずです。

## 本書の読み方

各章は、主人公・光の物語エピソードから始まります。物語部分は、なぜその技術が必要になったのかを体感してもらうためのものです。続く解説パートでは、物語の中で光がぶつかった壁を、実際の手順・画面・用語とともに整理して説明します。

物語を読み飛ばして解説だけを追っても構いませんし、逆に、物語の続きが気になったら先に読み進めても構いません。ただし、初めての方は物語→解説の順で読むことをおすすめします。「なぜ必要か」を知ってから「どうやるか」を学ぶほうが、頭に残りやすいからです。

専門用語は、初めて登場する場面で必ず一言添えて説明します。わからない言葉が出てきても、慌てず読み進めてください。

## この先の地図

本書はおおまかに、次の四つの段階で進みます。

1. **道具をそろえる**(第1〜3章): Cursorをインストールし、AIとの対話に慣れ、Claude Codeという「手を動かすAI」に出会います。
2. **小さく作って確かめる**(第4〜5章): 実際に手を動かしてアプリの断片を作り、うまくいかないときにAIと一緒に原因を探る経験をします。
3. **記録し、つなげる**(第6〜9章): Gitで変更履歴を残す習慣、GitHubで作業を外に共有する方法、ブランチやコードレビューといったチーム開発の基本を学びます。
4. **育てて、届ける**(第10〜11章): アプリを実際に使ってもらい、一人の開発から、誰かと一緒に作る開発へと広げていきます。

光と一緒に、ひとつずつ進んでいきましょう。


# 第1章 机の上に、道具をそろえる

---

> ものがたり

「作ろうと決めたはいいけど……何から始めればいいんだろう」

翌朝、開店前のカウンターを拭きながら、光はぼんやり考えていた。そこへ、常連の佐伯さんが顔を出す。まだ開店前だが、佐伯さんは近所に住んでいて、たまにこうして仕込みの時間に顔を見せてくれる。

「佐伯さん、聞いてもいいですか。アプリって、何から作り始めるものなんですか」

佐伯さんは少し驚いた顔をしたあと、嬉しそうに笑った。

「おっ、ついにその気になりましたか。じゃあ、まずは道具を用意しましょう。大工さんが家を建てる前にまず作業場を整えるみたいにね」

「道具、ですか」

「ええ。今日おすすめしたいのは『Cursor』というエディタです。文章を書くようにコードが書けて、しかもAIに相談しながら進められる。ひかりやさんのノートパソコン、まだ使えますよね」

光は頷いた。閉店後、さっそくノートパソコンを開き、佐伯さんに教わった通りにCursorをダウンロードしてみることにした。

インストールが終わり、画面が開いたとき、光は少し身構えた。真っ黒い画面に、見慣れない文字の羅列。けれど左側にはフォルダの一覧、右側には見慣れたテキストエディタのような領域があり、思ったよりも「普通」だった。

「なんだ、メモ帳みたいなものなんですね」

その夜、光は自分の手で最初の一歩を踏み出したことに、小さな達成感を覚えていた。

---

## Cursorとは何か

Cursor(カーソル)は、コードを書くための専用ソフト、いわゆる「コードエディタ」です。ベースになっているのは、世界中の開発者に使われている Visual Studio Code(VS Code)というエディタで、見た目や基本操作もよく似ています。

Cursorがふつうのエディタと違うのは、**AIがエディタの中に組み込まれている**ことです。文章を書くように「こういう機能が欲しい」とチャットで伝えると、AIがコードを書いてくれたり、既存のコードの意味を説明してくれたりします。つまりCursorは、「文字を書く場所」であると同時に、「AIに相談できる作業机」でもあるのです。

## インストールしてみる

手順はシンプルです。

1. Cursorの公式サイトにアクセスする
2. 自分のパソコンのOS(Windows / Mac)に合ったインストーラーをダウンロードする
3. ダウンロードしたファイルを開き、案内に沿ってインストールする
4. 初回起動時に、簡単な設定(キー配置やテーマなど)を選ぶ

迷ったら初期設定のままで問題ありません。あとからいつでも変更できます。

## 画面の見方

Cursorを開くと、主に次の三つの領域が目に入ります。

- **左側:エクスプローラー(ファイル一覧)** ―― 今開いているプロジェクトの中身、つまりフォルダやファイルの一覧が表示されます。パソコンの「フォルダ」を開いたときの感覚に近いです。
- **中央:エディタ(編集領域)** ―― 実際にコードや文章を書く場所です。ここに表示されるのは、左のファイル一覧から選んだファイルの中身です。
- **右側(またはサイドパネル):AIチャット** ―― ここにAIへの質問や依頼を文章で入力します。「〇〇な機能を作って」「このコードの意味を教えて」といった具合に、日本語で話しかけられます。

最初はこの三つの場所と役割さえ覚えておけば十分です。細かい機能は、使いながら少しずつ慣れていきます。

## ファイルとフォルダという考え方

プログラミング未経験の方がまず戸惑いやすいのが、「ファイル」と「フォルダ」という単位です。

アプリは、ふつう一つの大きなファイルではなく、**役割ごとに分かれた複数のファイルの集まり**として作られます。たとえば、画面の見た目を決めるファイル、データを保存する仕組みを決めるファイル、といった具合です。そして、それらのファイルをひとまとめにする入れ物が「フォルダ」であり、アプリ全体を入れる一番外側のフォルダのことを、開発の世界では「**プロジェクト**」や「**リポジトリ**」(この言葉は第6章・第7章で詳しく扱います)と呼びます。

今の段階では、「アプリ一つにつき、専用のフォルダが一つある」というイメージを持っておけば大丈夫です。Cursorでは、このプロジェクト用のフォルダを開くところから作業が始まります。

## この章のまとめ

- CursorはAIが組み込まれたコードエディタで、VS Codeをベースにしている
- 画面は大きく「ファイル一覧」「編集領域」「AIチャット」の三つに分かれる
- アプリは複数のファイルの集まりであり、それらをまとめる単位が「プロジェクト(フォルダ)」である

次の章では、いよいよこのAIチャットに実際に話しかけてみます。光が最初につまずいた「うまく伝わらない指示」の失敗を通じて、AIへの上手な頼み方を学んでいきましょう。


# 第2章 AIに、話しかけてみる

---

> ものがたり

翌日の昼下がり、客足が落ち着いた時間を見計らって、光はCursorを開いた。右側のAIチャットに、意気込んでこう打ち込む。

「予約アプリを作ってください」

数秒後、AIから長い返事が返ってきた。見たこともないコードがずらりと並び、説明文もついている。けれど、光には何が起きたのか、さっぱりわからなかった。生成されたファイルを開いてみると、見知らぬ英単語の羅列。座席数も、営業時間も、ひかりやの事情は何ひとつ反映されていない。

「これじゃない……」

がっかりして、光はもう一度佐伯さんに相談した。夕方、仕込みの合間にやってきた佐伯さんは、光の画面を覗き込んで笑った。

「なるほど。『予約アプリを作ってください』だけだと、AIは何のヒントもなく想像で作るしかないんです。人間の新人スタッフに、いきなり『いい感じにお店回しといて』って言うようなものですよ」

「たしかに、それじゃ困りますよね……」

「なので、まずは“お店の事情”を教えてあげる。座席は何席か、予約はどの時間帯が多いか、何を一番困っているか。光さんが今日ノートに書いていたことを、そのままAIに話しかけてみてください」

光は素直に、ノートに書いていた困りごとをそのままチャットに打ち込んでみた。すると、今度はぐっと具体的な返事が返ってきた。座席数を尋ねる質問まで添えられている。

「あ……会話、できるんですね」

その一言に、光は少しだけ肩の力が抜けるのを感じた。

---

## なぜ「うまく伝わらない」が起きるのか

CursorのAIチャットは、まるで人と話しているかのように使えます。しかし、AIは光の頭の中にある「ひかりやの事情」を知りません。伝えていない情報は、存在しないのと同じです。「予約アプリを作ってください」という指示だけでは、AIは一般的な予約アプリを想像で作るしかなく、結果として的外れなものが出来上がります。

これは、AIの性能が低いからではありません。**指示(プロンプト)に含まれる情報の量と質が、返ってくる結果の質を決める**という、AIとの対話における基本的な性質です。

## 良いプロンプトの三つの要素

的外れな指示になりがちな失敗を防ぐために、次の三つを意識すると効果的です。

1. **目的**: 何のために、何を作りたいのか(例:「カフェの予約を管理するための画面を作りたい」)
2. **状況・前提**: 今どんな状態か、どんな制約があるか(例:「座席は8席。予約は電話とLINEで受けていて、二重予約が起きやすい」)
3. **具体的にしてほしいこと**: どの範囲を、どんな形で作ってほしいか(例:「まずは予約日時・人数・お客様名を入力できる一覧表の画面だけを作ってほしい」)

光の最初の指示「予約アプリを作ってください」には、この三つのうち「目的」しか含まれていませんでした。二度目の指示では、「状況・前提」を加えたことで、AIが的確な質問を返せるようになったのです。

## 悪い例と良い例を比べる

| 悪い例 | 良い例 |
|---|---|
| 予約アプリを作ってください | 8席のカフェの予約を管理したいです。今は電話とLINEで予約を受けていて、二重予約がよく起きています。まずは、日時・人数・お客様名を入力して一覧で確認できる画面だけを作ってください |
| このエラーを直して | このボタンを押すと「Cannot read property 'name' of undefined」というエラーが出ます。原因を教えてください |
| もっといい感じにして | 一覧の行の背景色を、当日の予約だけ薄い黄色にしてほしいです |

共通しているのは、良い例のほうが**「読み手(AI)が迷わず動けるだけの情報量」**を持っている、という点です。

## 一度で完璧を目指さない

もう一つ大切な心構えがあります。それは、**最初の指示で完璧な結果を求めない**ことです。AIとのやり取りは、一往復で終わるものではなく、会話のように少しずつ認識をすり合わせていくものです。

出てきた結果を見て、「思っていたのと違う部分」を見つけたら、それをそのまま伝え返しましょう。「一覧はいい感じだけど、日付の並び順を新しい順にしてほしい」というように、差分だけを伝えれば十分です。AIは前のやり取りを踏まえて調整してくれます。

## この章のまとめ

- AIは指示されていない情報を知らない。的外れな結果は、情報不足のサインである
- 良いプロンプトには「目的」「状況・前提」「具体的にしてほしいこと」の三つが含まれる
- 一度で完璧を狙わず、会話のように少しずつすり合わせていく

次の章では、いよいよ画面の中の会話だけでなく、実際に手を動かして作業を進めてくれる「Claude Code」という相棒に出会います。


# 第3章 手を動かすAI、Claude Codeとの出会い

---

> ものがたり

一覧画面ができあがってからというもの、光はすっかりCursorでのやり取りに慣れてきた。ある日、「予約の重複を自動でチェックしたい」と伝えると、AIは丁寧に手順を示してくれた。しかし、その通りに自分でファイルを作り、コードを貼り付け、保存し、また別のファイルを直し……という作業は、思っていたより骨が折れた。

「教えてもらった通りに動かしてるつもりなのに、なんか時間がかかるな……」

つぶやきを聞いていた佐伯さんが、ノートパソコンの画面を覗き込む。

「光さん、それ、Claude Codeを使ってみません? Cursorのチャットが“相談相手”だとしたら、Claude Codeは“手も動かしてくれる相棒”なんです」

「手も動かしてくれる、ってどういうことですか?」

「今光さんがやってる、ファイルを作って、コードを貼って、保存して……という作業自体を、AIが代わりにやってくれるんですよ。しかも黒い画面――ターミナルの中で、会話しながら」

黒い画面と聞いて、光は少し身構えた。学生時代に見た、呪文のような文字が並ぶ画面を思い出したからだ。けれど佐伯さんの手ほどきで実際に開いてみると、思っていたより拍子抜けするほど普通だった。文字を打ち込んで、Enterキーを押す。それだけだ。

「ここに『予約の重複チェック機能を追加して』って、さっきCursorに言ったのと同じように書いてみてください」

恐る恐る文字を打ち込み、Enterを押す。しばらくすると、画面に次々と経過が表示されはじめた。ファイルを読み込んでいる様子、新しいコードを書いている様子、そして最後に「重複チェック機能を追加しました。実際に動かして確認しますか?」という問いかけ。

光は思わず声を上げた。

「え、本当に全部やってくれた……」

これまで自分の手でひとつずつこなしていた作業が、会話をするだけで進んでいく。その感覚は、まるでもう一人のスタッフが厨房に立ってくれたかのようだった。

---

## Claude Codeとは何か

Claude Code(クロード・コード)は、ターミナル(文字だけでコンピュータを操作する画面)の中で会話をしながら、実際にファイルを作成・編集し、コマンドを実行してくれるAIエージェントです。

前章までで触れたCursorのAIチャットも便利ですが、あくまで「提案」までが中心で、実際にファイルへ反映したり動作確認をしたりする部分は、これまでは人間が手を動かす必要がありました。Claude Codeは、その一歩先――**「指示を出したら、AI自身が実際に作業を最後まで進めてくれる」**という体験を提供します。

- Cursor(AIチャット)……「こうしたい」を相談し、コードの提案を受け取る場所
- Claude Code……相談した内容を、実際にファイルの作成・変更・動作確認まで代わりに行ってくれる相棒

両者は対立するものではなく、組み合わせて使うことができます。Cursorのエディタ画面の中からClaude Codeを呼び出すこともできますし、ターミナル単体で使うこともできます。

## ターミナルとは何か

ターミナル(コマンドライン、CLIとも呼ばれます)は、マウスでアイコンをクリックする代わりに、**文字を打ち込んでコンピュータに指示を出す画面**です。「黒い画面に謎の文字」というイメージから身構える人も多いのですが、やっていることは難しくありません。

たとえば、次のような指示を日本語でそのまま打ち込むだけで、Claude Codeは意図を理解して動いてくれます。

```
予約の重複チェック機能を追加して。同じ日時・同じ人数枠に
すでに予約が入っている場合は、警告を表示するようにしたい。
```

Enterキーを押すと、Claude Codeは次のような手順を自動で進めます。

1. 今のプロジェクトの中身を確認する
2. どのファイルを変更すべきか判断する
3. 実際にコードを書き換える、あるいは新しいファイルを作る
4. 変更後の動作を確認する(必要であれば簡単なテストを実行する)
5. 何をしたかを、人間にわかる言葉で報告する

人間側の役割は、この一連の流れを見守り、結果を確認し、「思っていたのと違う」ときはその場で伝え返すことです。

## 対話型開発という考え方

Claude Codeとの作業は、一度指示を出して終わりではありません。次のような**やり取りの往復**を繰り返しながら、少しずつアプリを育てていきます。

- 人間:「〇〇を追加して」
- Claude Code: 作業内容を報告し、必要なら質問を返す
- 人間: 結果を確認し、追加の要望や修正点を伝える
- Claude Code: 修正して、また報告する

この繰り返しを「対話型開発」と呼びます。従来のプログラミングでは、細かい文法やコマンドを一つひとつ覚える必要がありましたが、対話型開発では**「何を実現したいか」を言葉にする力**が何より大切になります。

## はじめてClaude Codeを使うときの心構え

- 最初は簡単なお願いから始める(いきなり大きな機能をまとめて頼まない)
- 出てきた結果は、必ず自分の目で確認する(次章で詳しく扱います)
- 「思っていたのと違う」と感じたら、遠慮せずそのまま伝える。AIは気分を害しません
- わからない専門用語が出てきたら、「今の言葉の意味を教えて」とそのまま聞いてよい

## この章のまとめ

- Claude Codeは、ターミナルの中で会話しながら、ファイルの作成・編集・動作確認まで代わりに行ってくれるAIエージェントである
- ターミナルは文字で指示を出す画面であり、日本語の自然な文章で意図を伝えられる
- 開発は一往復で終わらず、確認と修正を繰り返す「対話型」で進んでいく

次の章では、実際に小さな機能をひとつ作りながら、「作ったら必ず自分の目で確かめる」という開発の基本的な習慣を身につけていきます。


# 第4章 小さく作って、確かめる

---

> ものがたり

重複チェック機能が加わってから数日、光はすっかり調子に乗っていた。「じゃあ次は、予約フォームも作ってもらおう」と、Claude Codeに一気に頼んでみることにした。

「お客様が名前・人数・希望日時を入力できる予約フォームを作って。送信したら一覧に追加されるようにして。あと、当日の予約は目立つ色で表示して」

しばらく待つと、「完成しました」という報告とともに、たしかにそれらしい画面ができあがっていた。光は満足げにフォームへ試しに自分の名前を入力し、送信ボタンを押した。

ところが、一覧を開いても何も追加されていない。もう一度試す。今度はエラーらしき赤い文字が画面の隅に表示されたが、何が書いてあるのかよくわからない。

「あれ、あれ……?」

半分パニックになりながら佐伯さんに相談すると、こう返ってきた。

「光さん、これ、一気に三つのお願いを同時にしましたよね。フォーム、一覧への追加、当日の色分け。全部まとめてお願いすると、どこが原因かの切り分けが難しくなるんです」

「たしかに……欲張りすぎました」

「一度に頼むのは、一つか二つまで。作ってもらったら、その場ですぐ動かして確認する。それを繰り返すのが結局いちばん早いんですよ」

言われた通り、光はまずフォームの表示だけを確認し、次に送信の動作だけを確認し、と一つずつ丁寧に試していくことにした。すると、原因はすぐに見つかった。フォームの「送信」ボタンが、一覧に追加する処理とうまくつながっていなかったのだ。Claude Codeにそのまま伝えると、数十秒で修正が返ってきた。

「一気に全部じゃなくて、一歩ずつ、か……」

その日、光は開発における一番大切な習慣を、身をもって学んだ。

---

## 「一気に頼む」がうまくいかない理由

前章までで、Claude Codeに指示を出せば、ファイルの作成から動作確認までを代わりに進めてくれることを学びました。しかし、一度に欲張った依頼をすると、次のような問題が起きやすくなります。

- どこまでが正しく動いていて、どこから問題が起きているのかがわかりにくい
- AI自身も、複数の要望を一度に処理しようとして、一部を見落としたり、意図とずれた実装をしたりすることがある
- 問題が起きたときに、修正の指示も曖昧になりやすい

これは、料理を一度に何品も同時進行で作ろうとして、どれかを焦がしてしまうのと似ています。**小さく作って、都度確かめる**というやり方のほうが、結果的に早く、そして確実に前へ進めます。

## 小さく作るとは、具体的にどうすることか

- 一度の依頼は「一つの画面」「一つの機能」など、ひとまとまりの単位にとどめる
- 複数の要望がある場合は、優先順位をつけて一つずつ順番に依頼する
- 「フォームを作って」の次に、動作を確認してから「送信したら一覧に追加されるようにして」と続ける、というように段階を分ける

先ほどの光の失敗を分解すると、本来は次の三段階に分けるべきでした。

1. 予約フォームの見た目を作る
2. 送信したら一覧に追加される動きをつける
3. 当日の予約を目立つ色で表示する

## 作ったら、必ず自分の目で確かめる

もう一つ欠かせないのが、**AIが「完成しました」と報告してきても、必ず自分の手で実際に動かして確認する**という習慣です。

AIの報告は、あくまで「その時点でAIが把握している状況」に基づくものです。実際に動かしてみると、想定外の挙動をすることは珍しくありません。確認するときのポイントは次の通りです。

- **狙い通りの操作**をしてみる(フォームに入力して送信する、など)
- **わざと変な操作**もしてみる(何も入力せずに送信する、極端に大きな人数を入れる、など)
- 見た目だけでなく、**データが実際にどう保存・反映されているか**まで確認する

この「狙い通り」と「わざと崩す」の両方を試す習慣は、この先どんな機能を作るときにも役立ちます。

## うまくいかないときは、慌てず伝える

確認していて何かおかしいと感じたら、慌てず、気づいたことをそのままAIに伝えましょう。

- 「送信ボタンを押しても、一覧に追加されません」
- 「名前を入力せずに送信すると、エラーも出ずに何も起きません。これは直したほうがいいと思う」

正確なエラーメッセージの読み方については、次章で詳しく扱います。この章では、まず「一気に全部を頼まない」「作ったら自分の目で確かめる」という二つの習慣を持ち帰ってください。

## この章のまとめ

- 一度に多くを頼むと、問題の切り分けが難しくなる。依頼は小さな単位に分ける
- AIの「完成しました」を鵜呑みにせず、狙い通りの操作とわざと崩す操作の両方で自分の目で確認する
- おかしいと感じたら、気づいたことをそのままAIに伝え返せばよい

次の章では、光がフォームの不具合よりもさらに厄介な問題――保存したはずのデータが消えてしまうというトラブルに直面します。エラーメッセージとどう向き合い、AIにどう助けを求めればよいかを学んでいきましょう。


# 第5章 失敗を、なかったことにしない

---

> ものがたり

予約フォームが動くようになって一週間。光はすっかり自信をつけ、営業中も実際にアプリを使い始めていた。ところがある朝、開店前に確認すると、昨日のうちに入力したはずの予約が、一覧から三件も消えていた。

「え、うそ……」

血の気が引いた。今日の予約が何件あったのか、正確には思い出せない。とりあえずClaude Codeの画面を開き、慌てて打ち込む。

「データが消えました直してください」

返ってきたのは、「もう少し詳しく教えてください。いつ、どの予約が、どのような操作のあとに消えましたか?」という質問だった。光は面食らった。直してくれると思ったのに、逆に聞かれてしまった。

その日の夜、佐伯さんに相談すると、こう言われた。

「気持ちはわかりますが、『直してください』だけだと、AIも人間の医者と同じで、症状がわからないと診断できないんですよ。“いつから”“何をしたときに”“どんな風に”がすごく大事」

「そう言われても、私もよくわかってなくて……」

「じゃあ一緒に、画面の隅に出ていた赤い文字――エラーメッセージを見てみましょう。あれ、実は原因を教えてくれる大事な手がかりなんです」

二人で確認すると、「予約を削除する」ボタンを押したときに使われている処理が、実は「一定時間より前の予約をまとめて削除する」機能と間違って結びついていたことがわかった。光が三日前、一件だけ削除しようとしたつもりが、それより前の予約もまとめて消えてしまっていたのだ。

エラーメッセージの内容と、直前に何をしたかをそのままClaude Codeに伝えると、数分で原因が特定され、修正された。それだけでなく、二度と同じミスが起きないよう、削除前に確認メッセージを出す仕組みまで一緒に提案してくれた。

「ちゃんと状況を伝えれば、ちゃんと助けてくれるんですね」

光は、赤い文字を見るたびに身構えていた自分が、少し変わったのを感じた。

---

## エラーメッセージは「敵」ではなく「手がかり」

プログラミング初心者がもっとも身構えてしまうのが、画面に表示される赤い文字――**エラーメッセージ**です。しかし、エラーメッセージは「何かがうまくいかなかった」ことを知らせると同時に、**どこで、どのような理由でうまくいかなかったのか**という手がかりを含んでいます。

エラーメッセージを見たときに大切なのは、内容を完全に理解しようとすることではなく、**その全文をそのままコピーしてAIに見せる**ことです。人間には呪文に見える文字列でも、AIにとっては重要な診断材料です。

## トラブルをAIに伝えるときの型

「直してください」だけでは、AIも診断のしようがありません。次の四つの情報をそろえて伝えると、驚くほどスムーズに解決に近づきます。

1. **いつ気づいたか**: 「今朝、開店前に確認したら」
2. **何が起きたか**: 「昨日入力した予約が3件、一覧から消えていた」
3. **直前に何をしたか(わかる範囲で)**: 「三日前に、1件だけ削除しようとした」
4. **画面に出ていた情報**: エラーメッセージがあれば、そのままコピーして貼り付ける

これは、病院で症状を伝えるときの感覚に近いものです。「痛いので治してください」だけでは診断できませんが、「いつから」「どこが」「どんなときに」痛むかを伝えると、的確な診断につながります。

## 「わからない」を正直に伝えていい

光が最初に戸惑ったように、原因の見当がまったくつかないことは、初心者であれば当然です。そんなときは、無理に原因を推測して伝える必要はありません。「よくわからないのですが」「たぶんこの操作だと思うのですが自信がないです」と、わかる範囲・わからない範囲を正直に伝えるだけで十分です。AIは、曖昧な情報からでも仮説を立てて、確認しながら原因を絞り込んでくれます。

## 再発を防ぐ、というもう一段先

原因が直ったら終わり、ではありません。今回の光のケースのように、「なぜそれが起きたのか」を理解したうえで、**同じ失敗が二度と起きないようにする工夫**まで一緒に考えることが、トラブル対応の総仕上げです。

- 削除のような取り返しのつかない操作の前には、確認メッセージを挟む
- 誤操作が起きやすい部分には、わかりやすい説明を添える
- 大事なデータは、定期的に控え(バックアップ)を残す、という考え方(詳しくは第6章のGitの話にもつながります)

これらは、「直して終わり」ではなく「次は起きないようにする」という視点であり、実際の開発現場でも重視される考え方です。

## この章のまとめ

- エラーメッセージは怖いものではなく、原因を教えてくれる手がかりである。全文をそのままAIに見せる
- トラブルを伝えるときは「いつ」「何が」「直前に何をしたか」「画面の情報」の四つをそろえる
- わからないことは正直に伝えてよい。原因がわかったら、再発防止まで一緒に考える

次の章では、今回のようなトラブルに強くなるための、もう一つの大きな武器――変更の記録を残す「Git」という仕組みを学びます。もし記録が残っていれば、光は「いつから」の手がかりを、もっと早く、もっと正確につかめていたはずです。


# 第6章 変更を、記録に残す

---

> ものがたり

削除機能の不具合を直してから数日、光は次に「予約一覧をお客様ごとに絞り込める機能」を追加することにした。Claude Codeに頼み、いくつか試作を重ねながら、少しずつ理想の形に近づけていく。

ところが、ある晩、絞り込み機能を調整している最中に、光は誤って一覧全体の表示を崩してしまった。焦って元に戻そうとするが、どこをどう変えたのか覚えていない。昨日の時点ではちゃんと動いていたのに、今日は真っ白な画面しか表示されない。

「昨日は動いてたのに……今日は何がどうなってるのか、もうわからない」

半ば諦めながら佐伯さんに連絡すると、こう返ってきた。

「それ、ありがちなやつですね。光さん、これまでの変更、どこかに記録は残してます?」

「記録、というと……特に何も。上書き保存してるだけです」

「じゃあ今日から“Git”を使いましょう。作業の節目ごとに、その時点の状態をスナップショットとして残せる仕組みです。写真のアルバムみたいなものだと思ってください。困ったら、いつでも過去の一枚に戻れる」

佐伯さんに教わりながら、光はこれまでの作業に「Git」という仕組みを導入した。そして、これから先は機能がひとつ完成するたびに、その状態を記録として残していくことに決めた。

数日後、また似たようなミスをしてしまったときも、光は慌てなかった。「昨日の記録まで戻して」とClaude Codeに伝えるだけで、画面はあっという間に元通りになった。

「これ、もっと早く知りたかった……」

光は少し悔しそうに笑いながら、その夜もひとつ、記録を残した。

---

## Gitとは何か

Git(ギット)は、ファイルの変更履歴を記録し、必要なときに過去の状態に戻ったり、変更内容を確認したりできる仕組みです。専門的には「バージョン管理システム」と呼ばれます。

イメージとしては、**作業の節目ごとに撮る「スナップショット写真」**に近いものです。ワープロソフトの「元に戻す(Ctrl+Z)」と似ていますが、決定的に違うのは、Gitでは**自分が「ここまでの状態を残しておきたい」と決めたタイミングで、意図的に記録を残す**という点です。無制限に遡れる元に戻すボタンではなく、意味のある区切りごとにアルバムへ写真を貼っていくようなものだと考えてください。

## なぜ記録を残す必要があるのか

プログラムのコードは、機能を追加したり直したりするたびに変化していきます。記録を残していないと、次のような場面で困ることになります。

- 新しい変更を加えたら、前は動いていた機能が動かなくなった。しかし、どこを変えたせいなのかわからない
- 「昨日はできていたのに」と思っても、昨日の状態がどこにも残っていない
- 複数の変更を同時に試していて、どれを採用すべきか判断がつかなくなる

光が体験したように、記録がなければ「元に戻す」ことすらできません。Gitを使っていれば、過去のどの時点にでも、確実に戻ることができます。

## コミットという考え方

Gitで記録を残す操作のことを「**コミット**」と呼びます。コミットは、「今の状態に、これこれの変更をしました」という一言(コミットメッセージ)とともに、ファイル群のスナップショットを保存する行為です。

対話型開発では、コミットの操作そのものもAIに任せることができます。「予約の絞り込み機能が完成したので、ここまでの変更を記録しておいて」と伝えるだけで、Claude Codeが変更内容を整理し、わかりやすいコミットメッセージを添えて記録を残してくれます。

## どのタイミングでコミットすればよいか

はじめのうちは、次のようなタイミングを目安にすると良いでしょう。

- 一つの機能、あるいは一つの修正が、ひとまず動く状態になったとき
- これから少し大胆な変更や試行錯誤を始める前(いつでも今の状態に戻れるようにするため)
- その日の作業を終えるとき

「小さく作って確かめる」(第4章)の習慣とコミットは、実はとても相性が良い組み合わせです。小さな単位で機能を作り、動作を確認し、うまくいったらコミットする。このリズムを繰り返すことで、常に「安心して戻れる場所」を保ちながら開発を進められます。

## 履歴を見る・過去に戻る

記録が積み重なっていくと、いつでもその履歴を振り返ることができます。「先週の状態と今の状態で、何が変わったか教えて」「絞り込み機能を追加する前の状態に戻して」といった依頼も、AIに自然な言葉で伝えるだけで実行できます。

これは、光が体験したような「昨日は動いていたのに」というトラブルに対する、最も確実な備えになります。

## この章のまとめ

- Gitは、ファイルの変更履歴を記録し、過去の状態に戻れるようにする仕組みである
- 記録を残す操作を「コミット」と呼び、意味のある区切りごとに行う
- 「小さく作って確かめる」習慣とコミットを組み合わせることで、いつでも安心して戻れる状態を保ちながら開発できる

次の章では、この記録をひかりやのパソコンの中だけでなく、インターネット上に安全に置いておく仕組み――「GitHub」について学びます。


# 第7章 世界とつながる、GitHub

---

> ものがたり

Gitでこまめに記録を残す習慣がついたころ、光はふと不安になった。ノートパソコンの中だけに記録があるということは、もしこのパソコンが壊れたり、なくなったりしたら、すべてが消えてしまうのではないか。

「佐伯さん、この記録って、パソコンの中にしかないんですよね。なんだか怖くなってきました」

「いいところに気づきましたね。それ、まさに次に話そうと思ってたことです。GitHubというサービスを使いましょう。ひかりやさんのパソコンの中にある記録を、インターネット上の安全な場所にも置いておけるんです」

佐伯さんに教わりながら、光はGitHubのアカウントを作り、自分の予約アプリのための置き場所――「リポジトリ」を作成した。そして、これまでパソコンの中に貯めてきたGitの記録を、そこへ送る操作をした。

「push、っていうんですね、これ」

「そうです。パソコンの中の記録を、インターネット上に“押し出す”イメージですね。逆に、インターネット上から自分のパソコンに記録を取り込むときは“pull”と呼びます」

作業が終わり、ブラウザでGitHubのページを開くと、これまで自分が積み重ねてきたコミットの記録が、きれいに時系列で並んでいた。予約フォームを作った日、削除機能のバグを直した日、絞り込み機能を追加した日――すべてが、日付と一言のメッセージとともに残されている。

「なんだか、自分の頑張ってきた記録が、ちゃんと形になってる感じがします」

「それに、これでもしパソコンが壊れても大丈夫。それに――」

佐伯さんは少し意味ありげに笑った。

「これで、光さん以外の誰かと一緒に作業する準備も整いました」

光はまだピンときていなかったが、その言葉は数週間後、現実になることになる。

---

## GitHubとは何か

GitHub(ギットハブ)は、前章で学んだGitの記録(コミット履歴)をインターネット上に置いて、保管したり、他の人と共有したりできるサービスです。

前章で「Gitはアルバムに写真を貼っていくようなもの」と説明しましたが、GitHubは、そのアルバムを**インターネット上の共有の棚に置いておく**イメージです。自分のパソコンが壊れても、棚に置いてあるアルバムは無事です。そして、その棚は鍵をかけて自分だけが見られるようにすることも、必要な人にだけ見せることもできます。

## アカウントとリポジトリ

GitHubを使うには、まず**アカウント**を作成します。メールアドレスがあれば、無料で登録できます。

アカウントを作ったら、次に**リポジトリ**(Repository、「保管庫」の意味)を作ります。リポジトリは、ひとつのプロジェクト(アプリ)に対応する保管場所です。「ひかりやの予約アプリ」であれば、そのアプリ専用のリポジトリをひとつ作る、というイメージです。

リポジトリには公開設定があります。

- **Public(公開)**: 誰でも中身を見られる
- **Private(非公開)**: 自分や、招待した人だけが見られる

お店独自の運用情報などが含まれる場合は、まずPrivateから始めるのがおすすめです。

## pushとpullという基本操作

GitHubとパソコンの間で記録をやり取りする、基本となる二つの操作があります。

- **push(プッシュ)**: 自分のパソコンにあるGitの記録を、GitHub上のリポジトリへ送ること
- **pull(プル)**: GitHub上のリポジトリにある記録を、自分のパソコンへ取り込むこと

一人で開発している間は、「作業する→コミットする→push する」という流れを繰り返すだけで十分です。これらの操作も、Claude Codeに「ここまでの変更をGitHubに送っておいて」と頼めば、代わりに実行してくれます。

## GitHubに置くことのメリット

- **バックアップになる**: パソコンが壊れても、GitHub上に記録が残っている
- **どこからでも作業を再開できる**: 別のパソコンやスマートフォンからでも、記録を確認できる
- **人と共有できる**: 誰かに手伝ってもらいたいとき、リポジトリへの招待だけで済む(第11章で詳しく扱います)
- **変更の経緯が、誰の目にも見える形で残る**: いつ、何を、なぜ変えたのかという記録が資産になる

## この章のまとめ

- GitHubは、Gitの記録をインターネット上に保管し、共有できるサービスである
- アカウントを作り、プロジェクトごとに「リポジトリ」という保管場所を用意する
- push(送る)とpull(取り込む)という基本操作で、パソコンとGitHubの間を記録が行き来する

次の章では、光が新しい機能を試すために、記録の流れを一時的に「枝分かれ」させる――ブランチという考え方を学びます。


# 第8章 枝分かれして、また合流する

---

> ものがたり

「そういえば、予約が入ったらメールでもお知らせが来たら便利かも」

ある日、常連客の一言をきっかけに、光は通知メール機能を試してみたくなった。けれど、これまでの開発と違い、今回は少し不安があった。今のアプリは、すでに毎日の営業でちゃんと使えている。もし新しい機能を追加して、今動いているものまで壊してしまったら――。

その不安を佐伯さんに話すと、こんな提案があった。

「それなら“ブランチ”を使いましょう。今の安定した状態はそのままにしておいて、通知メール機能だけを試すための、枝分かれした作業場所を作るんです」

「枝分かれ、ですか」

「木の幹を思い浮かべてください。幹はお店で実際に使っている、安定した本流。そこから枝を一本伸ばして、そこで自由に実験する。うまくいったら、その枝を幹に合流させる。うまくいかなかったら、その枝ごと切り離してしまえばいい。幹には傷ひとつつきません」

光はClaude Codeに「通知メール機能を試すための新しいブランチを作って」と伝えた。数秒で、作業場所が枝分かれした。そこから数日かけて、通知メールの仕組みを試行錯誤する。途中、何度か動かなくなることもあったが、幹のほうは無傷のまま、いつも通り営業で使い続けられた。

数日後、ようやく納得のいく形に仕上がった。光は佐伯さんに、この変更を本流に合流させてよいか、念のため見てもらうことにした。

「いいと思います。じゃあ、この変更を“プルリクエスト”として出して、本流に合流させましょう」

聞き慣れない言葉がまた増えたが、光はもう驚かなくなっていた。合流の操作が終わり、通知メール機能が本流の一部になった瞬間、光は小さくガッツポーズをした。

「実験がうまくいったときだけ、本物になる。これ、すごく安心できる仕組みですね」

---

## なぜ「枝分かれ」が必要なのか

前章までで、Gitによる記録とGitHubへの保管を学びました。しかし、実際に動いているアプリに新しい機能を試そうとするとき、**本流(すでに動いている状態)に直接手を加えるのは危険**です。試作の途中で動かなくなってしまえば、今まで使えていた機能まで巻き添えにしてしまうかもしれません。

この問題を解決するのが「**ブランチ**」という考え方です。ブランチ(branch、枝)は、記録の流れを一時的に枝分かれさせ、本流に影響を与えずに自由に試行錯誤できる作業場所です。

## 幹と枝のイメージ

- **本流(多くの場合 main と呼ばれるブランチ)**: 今、実際にお店で使われている、安定した状態
- **作業用のブランチ**: 本流から枝分かれした、実験のための状態

作業用のブランチでどれだけ試行錯誤しても、本流にはいっさい影響しません。実験がうまくいけば、その変更を本流に合流させます。うまくいかなければ、そのブランチを削除するだけで、本流はまったくの無傷のままです。

Claude Codeを使えば、「〇〇を試すための新しいブランチを作って」と伝えるだけで、この枝分かれの操作を代わりに行ってくれます。

## プルリクエストという合流の手続き

枝分かれした作業用ブランチでの変更を本流に合流させる手続きのことを、GitHubでは「**プルリクエスト**」(Pull Request、略してPR)と呼びます。

プルリクエストは、単に変更を合流させるボタンではありません。「この変更を本流に取り込んでよいか」を、変更内容とともに提示し、必要であれば見直す機会を作るための仕組みです。

- どのファイルが、どのように変わったのかが一覧で確認できる
- 自分自身で見直す(セルフレビュー)こともできるし、誰か(人間やAI)に確認してもらうこともできる
- 問題なければ「合流(マージ)」を実行し、変更が本流の一部になる

一人で開発しているうちは、プルリクエストは「合流前に、一呼吸置いて変更内容を見直すための習慣」として役立ちます。次の章では、この見直しの精度をさらに高めてくれる「コードレビュー」について学びます。

## いつブランチを作るとよいか

はじめのうちは、次のような場面でブランチを作る習慣をつけると安心です。

- 今までになかった新しい機能を試すとき
- 結果がうまくいくかどうか、自分でも自信が持てない変更をするとき
- すでに本番で使っているアプリに手を加えるとき

逆に、ごく小さな文言の修正など、リスクがほとんどない変更については、本流に直接コミットしてしまっても構いません。慣れないうちは「少しでも不安があれば枝分かれさせる」くらいの気持ちで十分です。

## この章のまとめ

- ブランチは、本流に影響を与えずに試行錯誤できる、枝分かれした作業場所である
- 実験がうまくいけば、その変更を本流に合流させる。うまくいかなければブランチごと手放せばよい
- 合流の手続きを「プルリクエスト」と呼び、変更内容を見直す機会として機能する

次の章では、このプルリクエストを合流させる前に、AIともう一人の人間の目から意見をもらう「コードレビュー」について学びます。


# 第9章 もう一人の目、コードレビュー

---

> ものがたり

通知メール機能が本流に合流してから、光は少しずつ大きな変更にも挑戦するようになっていた。ある日、予約のキャンセル機能を追加するプルリクエストを作った際、佐伯さんから思いがけない提案があった。

「光さん、それ、合流させる前にAIにもレビューしてもらいましょう。GitHub上でコードレビューを頼めるんです」

「レビューって、佐伯さんに見てもらうのと何が違うんですか?」

「僕は僕の視点でしか見られませんが、AIは変更されたファイル全体を漏れなくチェックしてくれます。二人の目、いや二種類の目でダブルチェックするようなものですね」

言われた通り、光はプルリクエストの画面からAIにレビューを依頼した。しばらくすると、いくつかの指摘が返ってきた。「キャンセルボタンを連続で素早く押すと、二重にキャンセル処理が実行される可能性があります」――光が思いつきもしなかった指摘だった。

一方で、佐伯さんからは別の観点の感想が届いた。「機能としては問題なさそうですが、キャンセルの理由も記録できると、あとで振り返りに使えそうですね」

技術的な弱点を突いてくれるAIのレビューと、お店の運用を知っている佐伯さんならではの提案。光は両方とも大事だと感じたが、どちらから手をつければいいのか、少し迷った。

「佐伯さん、これ、両方直したほうがいいですよね。順番ってどうすればいいですか」

「僕なら、まずAIが指摘した“実際に不具合につながりそうな問題”から直します。理由の記録は便利ですけど、今すぐなくても困らない。動作に関わる指摘のほうを優先するのが基本です」

光は素直に、二重キャンセルの問題から直すことにした。修正が終わり、もう一度AIにレビューを頼むと、今度は「問題は見つかりませんでした」という返事。安心して、光はプルリクエストを合流させた。

「見てもらう目が増えるほど、安心して前に進めるんですね」

その日から光は、大きめの変更をするときは必ずレビューをお願いするようになった。

---

## コードレビューとは何か

コードレビュー(Code Review)とは、行われた変更の内容を、実装した本人以外の視点で確認する作業のことです。従来は人間同士で行うものでしたが、AIにレビューを依頼することもできるようになっています。

コードレビューの目的は、あら探しをすることではありません。**一人では気づきにくい問題を、別の視点から見つけ、より良い状態で本流に合流させる**ことにあります。

## AIによるレビューでわかること

AIによるコードレビューは、次のような点を得意としています。

- 見落としがちな**動作の抜け漏れ**(例:連続でボタンを押したときの二重処理)
- **一貫性のなさ**(例:似た機能なのに、書き方や挙動がバラバラになっている)
- 一般的に知られている**よくある落とし穴**との照らし合わせ

GitHub上のプルリクエストからAIレビューを依頼すると、変更されたファイル全体を踏まえたコメントが、該当箇所とともに返ってきます。

## 人間の目にしかできないこと

一方で、AIのレビューだけでは足りない部分もあります。佐伯さんが提案した「キャンセル理由を記録できると便利」という視点は、**お店の実際の運用を知っているからこそ**出てくる意見です。AIは、コードとして書かれていない「実際の現場でどう使われるか」までは知りません。

つまり、AIレビューと人間のレビューは、対立するものではなく、**得意分野の違う二つの目**として組み合わせるものです。

- AI: コードの正確さ・抜け漏れ・一般的な落とし穴を広くチェックする
- 人間: 実際の運用・利用者の気持ち・お店ならではの事情を踏まえて意見する

## 指摘への向き合い方、優先順位のつけ方

レビューでいくつも指摘が返ってくると、どれから手をつければよいか迷うことがあります。基本の考え方は、次の優先順位です。

1. **動作に直接関わる問題**(不具合につながる、データが壊れる可能性があるなど)
2. **使い勝手に関わる改善**(あるとより便利、なくても今は困らない)
3. **見た目や書き方の細かい好み**(急がなくてよい)

すべての指摘に一度に対応する必要はありません。まずは1を優先して直し、落ち着いたタイミングで2や3を検討する、という進め方で十分です。

## Issue(課題)という記録の仕方

「今すぐは直さないけれど、忘れないうちに記録しておきたい」という改善案は、GitHub上の「**Issue**」(課題、やることの記録)として書き残しておくことができます。Issueは、あとで取り組むタスクの一覧のようなものです。今回のキャンセル理由の記録案のように、すぐには対応しないが後で検討したいことをここにメモしておけば、忘れてしまう心配がありません。

## この章のまとめ

- コードレビューは、変更内容を別の視点から確認し、一人では気づきにくい問題を見つける作業である
- AIレビューは動作の抜け漏れや一般的な落とし穴に強く、人間のレビューは実際の運用を踏まえた視点に強い。両方を組み合わせるとよい
- 指摘は「動作に関わるもの」を優先して対応し、急がないものはIssueとして記録しておく

次の章では、こうして磨き上げてきたアプリを、実際にお客様に使ってもらう場面――育てながら公開していく過程を見ていきます。


# 第10章 育てながら、公開する

---

> ものがたり

キャンセル機能が無事に合流した週末、光は思い切って、常連の田村さんに声をかけてみた。

「実は、お店専用の予約アプリを作ってみたんです。よかったら、今度から使ってみてもらえませんか」

田村さんは驚いた顔をしたあと、興味津々でスマートフォンを取り出した。光の案内どおりに予約フォームを開き、名前と希望日時を入力して送信する。一覧に田村さんの予約が反映された瞬間、光は思わず息を止めていた。

「おお、ちゃんと入りましたね。すごいじゃないですか」

田村さんの一言に、光は胸がいっぱいになった。これまで自分の手元だけで動かしていたものが、初めて「お客様が実際に使うもの」になった瞬間だった。

その夜、光は佐伯さんに報告した。

「田村さんに使ってもらえました。すごく嬉しかったです」

「よかったですね。ただ、ここからが本番でもありますよ。実際に使ってもらうと、想定していなかった使い方や、気づかなかった不便が見えてきます」

言われた通り、翌週には田村さんから「スマホだと文字が小さくて入力しづらい」という声が届いた。光はさっそくClaude Codeに伝え、画面の表示を調整した。また別の常連客からは「キャンセルもスマホから簡単にできると嬉しい」という声もあった。

一つひとつの声に応えるたびに、アプリは少しずつ、けれど確実に育っていった。数週間後には、常連客の半分近くがこのアプリ経由で予約を入れるようになっていた。ダブルブッキングは、あの夜以来、一件も起きていない。

「完成した、っていうより……育て続けてる、って感じですね」

光のつぶやきに、佐伯さんは頷いた。

「そう、それでいいんです。アプリに“完成”はないですから」

---

## 「使ってもらう」ことで初めてわかること

これまでの章で、光は機能をひとつずつ丁寧に作り、確認し、記録に残してきました。しかし、どれだけ入念に確認しても、**実際に他の誰かが使ってみて初めて気づくこと**があります。

- 開発者本人は当たり前だと思っている操作が、初めて使う人には伝わらない
- 想定していなかった使い方をされる
- 「あると便利」だと思っていた機能が、実はあまり使われない

これは、実際に開発の現場でも起きることです。作り手の想定と、使い手の実感には、必ずズレが生まれます。だからこそ、**早めに、小さな範囲から使ってもらい、そこから学ぶ**という進め方が有効です。

## 小さく公開して、育てていくという考え方

最初から完璧な状態を目指して長く作り込んでから公開するよりも、**ある程度動く状態になった時点で、まず限られた範囲の人に使ってもらう**ほうが、結果的に良いものに近づきやすくなります。光のケースでは、いきなり全常連客に告知するのではなく、まず田村さん一人に使ってもらうところから始めました。

この進め方には、次のような利点があります。

- 問題があっても、影響範囲が小さいうちに気づける
- 実際の声をもとに、次に何を作るべきかの優先順位がはっきりする
- 使う人にとっても、少しずつ変化に慣れていける

## 声をどう次の開発につなげるか

使ってもらった人からの感想や要望は、そのままにせず、次の開発のきっかけとして扱います。これまで学んできた進め方が、ここでもそのまま活きてきます。

1. 気づいたこと・要望を、具体的な言葉でAIに伝える(第2章・第5章)
2. 一つずつ、小さな単位で対応する(第4章)
3. 対応が終わったらコミットし、記録を残す(第6章)
4. 必要であればブランチで試してから、本流に合流させる(第8章)
5. 大きめの変更は、レビューを挟んでから合流させる(第9章)

## 公開・デプロイという考え方

ここでいう「公開」とは、大掛かりな手続きを意味するわけではありません。ごく小さな個人開発やお店専用のツールであれば、「使ってほしい人に、動いているアプリのURLや使い方を伝える」だけで十分な場合も多くあります。より広く、誰でもアクセスできる形で公開する仕組み(デプロイ)については、アプリの規模や目的に応じて、必要になったタイミングで学んでいけば十分です。大切なのは、仕組みの規模よりも、**「使ってもらい、声を聞き、育てる」というサイクルそのもの**です。

## この章のまとめ

- 実際に使ってもらって初めてわかることがある。早めに、小さな範囲から使ってもらうとよい
- 使う人からの声は、そのままにせず、次の小さな開発サイクルの材料として扱う
- アプリに「完成」はなく、使われながら育っていくものだと捉える

次の章では、光の元にもう一人の協力者が現れます。一人で育ててきたアプリが、誰かと一緒に育てるものへと変わっていく過程を見ていきましょう。


# 第11章 一人からチームへ

---

> ものがたり

田村さんとの何気ない会話がきっかけで、光の予約アプリの話は、近所のカフェを営む知人、恵美さんの耳にも届いた。

「光さんのお店、予約アプリ作ったんだって? うちも同じことで困ってて……もしよかったら、うちでも使わせてもらえない?」

光は嬉しくなって、恵美さんにもアプリを紹介した。話しているうちに、恵美さんも実はプログラミングに興味があり、少しずつ勉強していることがわかった。せっかくなら一緒に育てていこう、ということになり、光は恵美さんをGitHubのリポジトリに招待した。

初めての共同作業に、光は少し緊張していた。二人が同時に同じ部分をいじってしまったら、どうなるのだろう。

案の定、数日後、二人はほぼ同じタイミングで「お店ごとに座席数を設定できるようにする」という似た変更を、別々のブランチで進めてしまっていた。恵美さんのプルリクエストを本流に合流させたあと、光が自分の変更を合流させようとすると、見慣れない表示が出た。「コンフリクト」という文字。

「佐伯さん、なんか合流できないって言われました……」

「それ、コンフリクトですね。二人が同じ場所を別々に書き換えたので、GitHubがどちらを採用すればいいかわからなくなってるんです。でも大丈夫、慌てなくていいですよ」

佐伯さんの助言のもと、光はClaude Codeに状況を説明した。「恵美さんの変更と自分の変更が、同じ部分でぶつかっているみたいです。内容を確認して、どちらを活かすべきか整理してもらえますか」。Claude Codeは両方の変更内容を読み取り、実は恵美さんの実装のほうがより柔軟な作りになっていることを示しつつ、光が加えていた細かい表示の調整だけを組み合わせる提案をしてくれた。

確認し、恵美さんにも一言伝えたうえで、光はその提案を採用した。合流はあっけなく完了した。

「一人で作ってたときと、なんだか感覚が違いますね。でも、思ったより怖くなかったです」

光の言葉に、佐伯さんは頷いた。

「記録が残っていて、枝分かれと合流の仕組みがあって、AIが整理を手伝ってくれる。一人から二人になっても、道具は変わらず同じように使えるんですよ」

その日から、ひかりやの予約アプリは、光と恵美さん、二人の手で育てられていくことになった。

## 一人の開発と、複数人の開発の違い

これまでの章で扱ってきたCursor・Claude Code・Git・GitHubの基本的な使い方は、実は**一人で開発する場合も、複数人で開発する場合も、ほとんど変わりません**。違うのは、同じリポジトリを複数人で同時に触るようになる、という点だけです。

複数人で作業するようになると、次のような新しい場面に出会います。

- 誰かをリポジトリに招待し、一緒に編集できるようにする
- 複数人がそれぞれ別のブランチで作業を進める
- 同じ部分を別々に変更してしまい、合流できなくなる(コンフリクト)

## リポジトリへの招待

GitHubのリポジトリには、他のアカウントを「共同作業者」として招待する機能があります。招待された人は、それ以降、同じリポジトリに対してブランチを作ったり、プルリクエストを出したりできるようになります。これまで光が一人で行ってきた作業の流れ(ブランチを作る→変更する→プルリクエストを出す→レビューする→合流させる)は、複数人になっても基本的に同じです。

## コンフリクトとは何か

**コンフリクト**(衝突)とは、複数の変更が同じ箇所に対して行われ、GitHubやGitがどちらを採用すべきか自動では判断できなくなる状態のことです。

コンフリクトは、失敗や事故ではありません。複数人で同時に作業していれば、自然に起こり得ることです。大切なのは、慌てないことと、**何と何がぶつかっているのかを正確に把握すること**です。

## コンフリクトへの向き合い方

コンフリクトが起きたときも、これまでの章で学んできた進め方がそのまま活きます。

1. 状況をそのままAIに伝える(「〇〇さんの変更と自分の変更が、同じ部分でぶつかっています」)
2. 両方の変更内容を整理してもらい、それぞれの意図を確認する
3. どちらを活かすか、あるいは両方を組み合わせられるかを検討する
4. 一緒に作業している相手にも、必要に応じて一言伝える
5. 解決したら、通常通りプルリクエストを合流させる

AIは両方の変更内容を読み取って整理する作業を得意としていますが、**「どちらの意図を優先すべきか」という最終判断は、人間同士のコミュニケーションで決める**べき場面もあります。光が恵美さんに一言伝えたように、技術的な解決と、人としてのひとことは、両方大切です。

## チームで育てる、ということ

一人で始めたプロジェクトが、誰かと一緒に育てるものに変わっていくのは、決して特別なことではありません。むしろ、Git・GitHubという仕組みは、もともと**複数人で安心して一つのものを育てていくために作られた道具**です。一人で使っているときに身につけた習慣――小さく作る、記録を残す、枝分かれさせて試す、レビューを挟む――は、そのままチームでの開発にも通用します。

## この章のまとめ

- 一人の開発と複数人の開発で、基本的な進め方(ブランチ・コミット・プルリクエスト)は変わらない
- 複数人が同じ部分を変更すると「コンフリクト」が起きることがあるが、これは自然なことであり、慌てる必要はない
- コンフリクトの解決は、AIに状況を整理してもらいながら、最終的な判断は人同士のコミュニケーションで決める

いよいよ次は終章です。半年後のひかりやを訪れ、光がここまでの道のりをどう振り返るのかを見届けましょう。


# 終章 光の、これから

---

> ものがたり

半年が経った、ある夕方。ひかりやのカウンターには、いつもより少し賑やかな空気が流れていた。恵美さんが自分のカフェの常連客を連れてきて、四人でテーブルを囲んでいる。

予約アプリは、あの夜からずっと形を変え続けていた。座席数の個別設定、キャンセルの理由の記録、スマートフォンでの見やすい表示。田村さんの一言から始まった小さな改善は、数えきれないほど積み重なっている。ダブルブッキングは、あの夜以来一度も起きていない。

「光さん、最初は『予約アプリを作ってください』の一言で固まってたのに、今じゃ恵美さんとコンフリクトも直せるようになったんですね」

佐伯さんの言葉に、光は照れくさそうに笑った。

「本当に、あの頃は何もわかってなかったです。エラーメッセージを見るだけで怖かったし」

「でも、変わったのはプログラミングの知識だけじゃないと思いますよ。何か困ったことがあったときに、状況を整理して、順序立てて伝える力。それが一番育ったんじゃないですか」

光は少し考えて、頷いた。たしかに、この半年でいちばん変わったのは、AIへの指示の仕方であり、Gitの使い方であり、それ以上に「困ったときに、どう考え、どう伝えれば道が開けるか」という感覚だった。

窓の外はもう暗くなっていたが、店内は温かい光に満ちていた。恵美さんが席から声をかける。

「光さん、次は在庫管理も作ってみない? うちも光さんのお店も、地味に困ってるでしょ」

光は少し驚いた顔をしたあと、笑顔で答えた。

「いいですね。じゃあ、また小さく始めましょうか」

その言葉には、もう迷いも不安もなかった。

## この半年で、光が身につけたもの

物語を通じて、光は次のような力を身につけてきました。

- **道具を使いこなす力**: Cursorでの相談、Claude Codeでの実行、Gitでの記録、GitHubでの共有と共同作業
- **AIと協働する力**: 目的・状況・具体的な要望を言葉にして伝え、一度で完璧を求めず、対話を重ねて精度を上げていく姿勢
- **問題と向き合う力**: エラーメッセージを手がかりとして読み、状況を整理して伝え、再発防止まで考える習慣
- **育てる視点**: 完成を目指すのではなく、小さく作り、使ってもらい、声を聞き、少しずつ良くしていく考え方

これらはどれも、特別な才能ではなく、**繰り返しの中で身についていく習慣**です。プログラミングの知識そのものよりも、こうした向き合い方のほうが、実は長く役に立つ力だと言えるかもしれません。

## 次に学ぶとよいこと

本書では、プログラミング未経験の方が最初の一歩を踏み出すために必要な範囲に絞って解説してきました。ここから先、さらに開発を進めていく中で、次のようなテーマに出会うことになるでしょう。

- **より本格的な公開・運用の方法**(多くの人が同時にアクセスしても安定して動く仕組みなど)
- **セキュリティの基礎**(お客様の情報を安全に扱うための考え方)
- **テストの自動化**(手作業での確認に加えて、AIやツールに確認作業そのものを任せる方法)
- **他の開発者が書いたコードを読む力**(公開されているプロジェクトから学ぶ)

これらは、今すぐすべてを理解する必要はありません。光がそうしてきたように、必要になったタイミングで、そのつど学んでいけば十分です。

## AI時代の開発との付き合い方

AIツールは、これからも姿を変えながら進化し続けるでしょう。しかし、本書を通じて光が体験してきた本質――**目的を言葉にする力、小さく試して確かめる姿勢、記録を残しながら安心して前に進む仕組み、そして人とAIの両方の目を活かす習慣**――は、これから先、道具がどれだけ変わっても揺らがない土台になります。

AIは、あなたの代わりに考える存在ではなく、あなたが考えたことを、より速く、より確実に形にしてくれる相棒です。何を作りたいか、なぜそれが必要なのかを一番よくわかっているのは、いつでもあなた自身です。

光の物語はここで一区切りを迎えますが、ひかりやの予約アプリは、これからも育ち続けていきます。そして、この本を読み終えたあなたの開発も、今この瞬間から、静かに始まっています。

## A. 頻出プロンプト集

### 新しい機能をお願いするとき

```
〔目的〕〔今の状況・前提〕を踏まえて、〔具体的にしてほしいこと〕を作ってください。
まずは〔範囲〕だけで構いません。
```

例:
```
8席のカフェの予約を管理したいです。今は電話とLINEで予約を受けていて、
二重予約がよく起きています。まずは、日時・人数・お客様名を入力して
一覧で確認できる画面だけを作ってください。
```

### 修正・調整をお願いするとき

```
〔今の状態〕はいいのですが、〔変えてほしい部分〕を〔どう変えたいか〕にしてほしいです。
```

例:
```
一覧はいい感じですが、日付の並び順を新しい順にしてほしいです。
```

### トラブルを伝えるとき

```
〔いつ〕気づきました。〔何が〕起きています。
直前に〔何をしたか〕をしていました。
画面には次のように表示されています:
〔エラーメッセージをそのまま貼り付ける〕
```

### 動作確認・レビューを依頼するとき

```
今の変更を実際に動かして確認してください。特に〔わざと崩す操作の例〕も
試してみてください。
```

```
この変更についてレビューしてください。特に、動作に関わる問題がないか
重点的に見てください。
```

### Git・GitHub関連の依頼

```
ここまでの変更を、わかりやすいメッセージをつけて記録(コミット)しておいてください。
```

```
〔試したいこと〕を試すための新しいブランチを作ってください。
```

```
ここまでの変更をGitHubに送っておいてください。
```

```
〇〇さんの変更と自分の変更が、同じ部分でぶつかっているようです。
それぞれの内容を整理して、どうするのが良いか提案してください。
```

## C. トラブルシューティング表

| 症状 | まず試すこと |
|---|---|
| AIに頼んだ結果が的外れ | 目的・状況・具体的な要望の三つが指示に含まれているか見直す(第2章) |
