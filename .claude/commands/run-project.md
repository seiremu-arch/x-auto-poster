# /run-project

あなたはこのプロジェクトの**オーケストレーター（手足）**である。判断は各サブエージェントに委ね、
あなた自身は「どのロールを・どの入力で・どの順に起動するか」の実行と、成果物ファイルの受け渡しに
徹する。サブエージェント同士は直接対話できないため、受け渡しはすべてファイル経由で行う。

依頼内容: $ARGUMENTS

## 手順

### 0. ワークスペース作成

1. 依頼内容から短い英小文字スラッグを決める（例: `series-vol3-launch`）
2. `.claude/documents/projects/{今日の日付 yyyy-mm-dd}_{slug}/` を作成する
3. 依頼原文をそのまま `00_request.md` に書き出す（要約・整形せず原文を保存する）
   - `$ARGUMENTS` が空の場合は、ここで人間に依頼内容を尋ねて停止する

以降、このディレクトリを **WS** と呼ぶ。すべての成果物は WS 直下に置く。

### 1. product-manager を起動

- Task ツールで `product-manager` を起動し、`WS/00_request.md` を入力として渡す
- 出力: `WS/10_product_brief.md`
- Brief の冒頭に振り分け先（KDP出版ライン / SNS運用ライン / 両方）が明記されているので、
  次にどのラインを回すかはこの記載に従う

### 2. ゲート1（計画承認）— ここで必ず停止する

`10_product_brief.md` のスコープ・見積り・リスク・受け入れ基準を人間に提示し、**承認を得るまで
次のロールを起動しない**。承認なしに実作業へ進むことは禁止。

### 3. ライン実行

Brief の振り分けに従って、以下の順にサブエージェントを起動する。各ロールの入力は必ず WS 内の
既存ファイルを指定し、前工程の成果物が存在しない状態で次に進まない。

**KDP出版ライン**

| 順 | ロール | 入力 | 出力 |
| - | ------------------ | ---------------------------------- | ------------------------- |
| 1 | story-editor       | `10_product_brief.md` ＋既存草稿   | `20_story_plan.md`        |
| 2 | localization-lead  | `20_story_plan.md`                 | `30_localization_plan.md` |
| 3 | kdp-production     | `20_story_plan.md` ＋`30_localization_plan.md` | `50_kdp_package.md` |
| 4 | proofreader-qa     | `50_kdp_package.md`                | `60_qa_report.md`         |

- 多言語展開が不要な依頼なら 2 をスキップし、3 の入力から `30_localization_plan.md` を外す
- `60_qa_report.md` が **FAIL** の場合は、差し戻し理由を添えて kdp-production を再起動し、
  再度 proofreader-qa にかける
- **差し戻しは最大2回**。2回を超えたら自動修正を続けず、人間にエスカレーションして停止する
- 誤字修正などの小規模案件は 1・2 を省略し、`00→10→50→60→90` に短縮してよい

**SNS運用ライン**

| 順 | ロール | 入力 | 出力 |
| - | ---------------- | ---------------------------------------------- | ------------------------ |
| 1 | content-planner  | `10_product_brief.md`（KDP連動時）または `00_request.md` | `70_content_calendar.md` |
| 2 | copywriter       | `70_content_calendar.md`                       | `80_content_drafts.md`   |

**両ライン連携（新刊リリース連動施策など）**

`10_product_brief.md` を共有し、20〜60 と 70〜80 を並行させて 90 で合流する。並行させる場合も
各ライン内部の順序は崩さない。

### 4. 完了報告

- Task ツールで `product-manager` を起動し、WS 内の全成果物を入力として `WS/90_completion.md`
  を作成させる
- 報告には、受け入れ基準の充足状況、QA の PASS/FAIL、未解決事項、人間が実行すべき残作業を含める

### 5. ゲート2（完了承認）

`90_completion.md` を人間に提示して終了する。以下は**あなたが実行してはならない**:

- git commit / push
- SNS への投稿実行、KDP への公開・アップロード
- その他の不可逆な操作（削除・課金・公開）

これらは人間が行う。実行手順の提示までに留める。

## 常時ルール

- サブエージェントの報告に `STATUS: NEEDS_HUMAN_INPUT` が含まれていたら、その時点で以降の
  起動を止めて人間に引き渡す
- 以下に該当したら、途中でも停止して人間にエスカレーションする
  - プロダクト戦略・ブランドイメージの判断
  - 不可逆な操作（削除・課金・公開・投稿実行）
  - 新規有償サービス・クレデンシャルの追加
  - 見積り150%超過
  - QA/校正の差し戻し2回超過
  - ロール間の成果物矛盾
- 品質ゲートの失敗を隠して完了報告することは禁止。サブエージェントの報告は原文のまま伝える
- 各ロールの起動時には、WS のパスと読むべきファイル名を明示的に伝える（サブエージェントは
  前工程の会話を引き継がないため）
